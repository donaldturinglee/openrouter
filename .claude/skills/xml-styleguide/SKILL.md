# Google XML document format style guide

Apply the [Google XML Document Format Style
Guide](https://google.github.io/styleguide/xmlguide.html) (version 1.0,
2008) when designing new XML document formats, meaning their schemas and the
prose specifications around them, and when writing instances. It targets XML
that machines generate and consume, not documents written for people.

Each rule below carries the RFC 2119 keyword the guide assigns it, in
parentheses. The guide's rationales explain the rules but are not rules.

## When the guide does not apply

-   Existing designs: the guide asks for no retroactive changes, and an
    extension follows the extended format's implicit style, even where that
    contradicts the guide.
-   Rich text: XHTML should be formatted like HTML, and formats such as ODF
    are out of scope. Machine-readable parts of a mixed document still
    follow the guide (SHOULD).
-   XML translated from protocol buffers or from any other format.
-   Group design efforts, public or private, where the guidelines inform the
    discussion but should not override what the group agrees.

Application note: tool-owned XML, such as build files, Android resources,
SVG, or XSLT, is an existing format; follow its schema and conventions.

Explicit user instructions, existing schemas and consumer contracts, the
project's serializer and validation setup, and local conventions take
precedence. Do not rename elements, change namespaces, or restructure a
format with consumers merely to apply the guide; keep style-only cleanup
separate from behavior changes, and explain material deviations. The guide
itself prefers breaking any rule, even a MUST, to producing a crude design.

## Before designing a format

-   Reuse an existing format if at all possible, ideally an extensible one.
    A new format is costly: design it with care (the guide cites [Tim Bray's
    essay](https://www.tbray.org/ongoing/When/200x/2006/01/08/No-New-XML-Languages))
    and seek the widest review you can, outside your organization too.
-   When reusing a format, use its prescribed elements and attributes
    sensibly, creatively if need be, without repurposing them; a required
    item that does not apply can, as a last resort, hold a fixed string.

## Schemas

-   Define the format with a schema (SHOULD) in RELAX NG compact syntax
    (SHOULD), optionally with embedded Schematron rules for cross-element
    and cross-attribute constraints (MAY).
-   Write one rule per element, "Salami Slice" style (SHOULD); a short,
    simple schema may mirror the document, "Russian Doll" style (MAY); avoid
    "Venetian Blind", one rule per element type (SHOULD NOT).
-   Supply regular expressions for complex values (SHOULD), and DTDs or W3C
    XML Schemas where existing tools or users need them (MAY).

## Namespaces

-   Put element names in a namespace (MUST), except when extending an older
    namespace-free document type, and make it the default (SHOULD).
-   Leave attribute names unqualified (SHOULD NOT namespace them) unless
    they come from, or are meant for, another document type.
-   Namespace names are HTTP URIs shaped like
    `https://example.com/inventory/2026` (SHOULD): a unique segment for the
    service or document type, optional further segments, then the year of
    creation.
-   Change a namespace only for drastically incompatible changes in meaning
    (MUST NOT otherwise), since every client must then change.
-   Keep prefixes short but distinctive enough not to collide (SHOULD),
    never one letter (MUST NOT), and lowercase ASCII letters only (SHOULD).

## Names

These rules cover element names, attribute names, and enumerated values.

-   Use lowerCamelCase (MUST) built from ASCII letters and digits only
    (MUST).
-   Stay within 25 characters (SHOULD) through concise, informative
    wording, unless that would make the name obscure.
-   Use only well-known published abbreviations (MAY), never ad hoc ones
    (MUST NOT), and camel-case acronyms as words (MUST): `sourceUrl`, not
    `sourceURL`.

## Elements and attributes

-   Each element holds nothing, only character data, or only child
    elements (MUST); no mixed content (MUST NOT), except in textual formats.
-   Skip elements that merely wrap a repeated child (SHOULD NOT use them).
-   Never depend on attribute order (MUST NOT), and never put values whose
    line breaks matter in attributes (MUST NOT), since parsers turn those
    breaks into spaces.
-   Limit attributes to roughly 10 per element (SHOULD NOT exceed), moving
    closely related ones into a child element.
-   Accept either quote character around attribute values (MUST).

## Values

-   Numbers: base-10 `xsd:int`, `xsd:long`, or `xsd:double` (SHOULD), or
    unbounded `xsd:integer` where truly required (MAY).
-   Booleans: prefer an enumeration (SHOULD NOT use booleans); if one is
    unavoidable, write `true` or `false` (MUST), never `1` or `0` (MUST
    NOT).
-   Dates: RFC 3339, with UTC rather than local times (SHOULD), though local
    time sometimes carries real information.
-   No embedded syntax that needs its own parser (SHOULD NOT), apart from
    dates, URIs, and XPath expressions.
-   Whitespace: parsers keep it in element content but turn newlines into
    spaces in attributes, and frameworks may strip more, so state the
    format's stripping rules (SHOULD).

## Key-value pairs and binary data

-   Write a simple pair as an empty element named for the key, with the
    value in a `value` attribute (SHOULD), an optional `unit` attribute
    (MAY), and SI units for physical quantities (SHOULD).
-   For very many or unbounded keys, one generic element may carry the pair
    in `key` and `value` attributes, adding `unit` and a domain-separating
    `scheme` where needed (MAY); then publish the keys with plain-language
    explanations somewhere.
-   Encode binary data as Base64, never raw (MUST); its line breaks may go
    (MAY), and `xsi:type="xs:base64Binary"` may label it (MAY). Linking to
    large data instead is a judgment call.

This original instance follows these rules:

```xml
<stationReport xmlns="https://example.com/weather/2026" station="ksea">
  <airTemperature value="285.4" unit="K"/>
  <windSpeed value="4.2" unit="m/s"/>
  <observedAt>2026-11-03T14:00:00Z</observedAt>
</stationReport>
```

## Processing instructions

-   Create no new processing instructions (MUST NOT), except for purely
    local conventions, which are still best avoided (SHOULD); use elements.
    Existing standardized ones are fine (MAY).

## Document instances

These guidelines are for writing instances: serializers often decide the
output, and no parser may rely on the guidelines, so always read XML with a
standard parser.

-   Use UTF-8 (SHOULD), barring extremely compelling reasons.
-   Declare namespaces on the root element where possible (SHOULD), keep
    one prefix per namespace throughout the document and its documentation
    (SHOULD), and use the customary prefixes for standard namespaces, such
    as `xs:` for XML Schema, `dc:` for Dublin Core, and `html:` for XHTML.
-   Avoid redundant whitespace in tags (SHOULD NOT): one space before each
    attribute, or a newline in a long start-tag (MAY).
-   Write empty elements as `<x/>` or `<x></x>` (MAY), and never treat the
    two differently.
-   Pretty-print, if at all, with 2-space indentation for children (MAY);
    never wrap character content (SHOULD NOT), which alters it; break long
    start-tags only after an attribute value other than the last (MAY).
-   Allow either quote style for attributes (MAY): a specification may
    neither demand nor ban one (MUST NOT), and `&quot;` and `&apos;` escape
    either.
-   Keep real data out of comments (MUST NOT) and comments out of publicly
    transmitted documents (SHOULD NOT); hand-written XML may hold TODO
    comments (MAY). Put comments only in the prolog or in elements with
    child elements, never beside character content, pretty-printed like
    elements with wrapped text and whitespace inside `<!--` and `-->`
    (SHOULD).
-   CDATA sections are allowed and mean the same as escaping with `&amp;`
    and `&lt;` (MAY); a specification may neither demand nor ban them (MUST
    NOT).
-   Use no entity references beyond `&lt;`, `&gt;`, `&amp;`, `&apos;`, and
    `&quot;` (MUST NOT). Character references are allowed (MAY), but prefer
    literal characters unless the encoding is not UTF-8; textual formats
    are exempt.

## Choosing elements or attributes

The guide gives considerations, not rules: elements suit repeatable,
structured, ordered, multi-line, large, or natural-language data and data
users should see; attributes suit codes, metadata, identifiers, references,
inherited values, and token lists; random mixtures are best avoided. Read
[elements versus attributes](references/elements-vs-attributes.md) when a
design decision turns on the choice.

## Check the change

-   Check well-formedness with a standard parser, and validate instances
    against the schema with the project's configured validator; do not add
    tooling solely for this skill.
-   Run consumer tests when a format changes: renamed elements, changed
    namespaces, or newly required content break clients.
-   Formatting proves nothing about the design, and re-wrapping character
    content changes its value.
-   For a review-only request, report findings (location, rule, minimal fix)
    without editing files.
